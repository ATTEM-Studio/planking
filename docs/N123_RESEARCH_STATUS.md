# PLANKING N1/N2/N3 역공학 진행 기록

> 마지막 업데이트: 2026-08-31
> 목적: ADLOG의 플레이스 지수 N1/N2/N3 구조를 검증하고, PLANKING에서 확정값/추정값을 구분해 구현하기 위한 연구 로그.

## 1. 현재까지 확인한 ADLOG 설명

ADLOG 공지 기준 설명:

- **N1**: 유사도 기준 — 키워드 + 네이버 로직과 업체정보의 유사성을 기준으로 측정되어 보이는 추정 데이터
- **N2**: 관련성 기준 — 키워드 및 리뷰, 저장, 트래픽 등 네이버 로직에 의해 측정되어 보이는 추정 데이터
- **N3**: 랭킹 기준 — 키워드의 플레이스 순위 기준으로 측정되어 보이는 추정 데이터

주의: ADLOG는 이를 네이버가 사용하는 숨겨진 내부 점수라고 설명하지만 동시에 `측정되어 보이는 추정 데이터`라고 표현한다. 따라서 PLANKING에서는 원천이 확정되기 전까지 **네이버 공식 제공 점수로 표기하지 않는다.**

## 2. DevTools로 확인한 데이터 흐름

### Naver 검색 측

네이버 검색의 `getRestaurants` GraphQL 응답에서는 다음 값들을 직접 확인할 수 있었다.

- MID / 업체명 / 카테고리 / 주소
- `visitorReviewCount`
- `blogCafeReviewCount`
- `saveCount`
- 리뷰 텍스트, 이미지, POS 관련 일부 정보 등

그러나 테스트한 일반 검색 응답에서는 ADLOG의 현재 N1/N2/N3 숫자와 `place_index`, `gdid` 계열 필드를 직접 발견하지 못했다.

현재 결론: **일반 네이버 검색 프론트 응답에서 ADLOG N1/N2/N3 완성값이 그대로 노출되는 것은 확인하지 못함.**

### ADLOG 측

플레이스 키워드 분석 실행 시 핵심 XHR 요청을 확인했다.

- Endpoint: `naver_place_list_exec.php`
- Method: POST
- Payload 예시:
  - `api_section=10`
  - `api_type=95`
  - `keyword=하단고기집`
  - `n=h`
  - `display=50`

브라우저는 사실상 **키워드와 출력 개수만 전달**하며, 응답에서는 업체별 완성 데이터가 내려온다.

응답 주요 필드:

- `place_rank`
- `place_id`
- `place_blog_cnt`
- `place_visit_cnt`
- `place_save_cnt`
- `place_index1`
- `place_index2`
- `place_index3`
- `place_gdid_inde1_compare`
- `place_gdid_inde2_compare`
- `place_gdid_inde3_compare`

따라서 **ADLOG 브라우저 자바스크립트가 N1/N2/N3를 계산하는 구조는 아님**을 확인했다. 지수의 획득 또는 계산은 ADLOG 서버 측에서 이루어진다.

아직 미확정인 부분:

1. ADLOG 서버가 별도의 Naver endpoint에서 내부 점수를 직접 가져오는지
2. 여러 Naver 원천 신호를 변환하는지
3. ADLOG 서버가 자체 역추정 모델로 계산하는지

이 부분은 클라이언트 DevTools만으로는 확인할 수 없다.

## 3. 동일 MID 교차 키워드 실험

같은 시점에 50개씩 수집한 세 키워드를 MID 기준으로 교차 비교했다.

### 기준 MID: 1800550902

`부산삼겹살 하단본점 숯불갈비`

| 키워드 | 순위 | N1 | N2 | N3 |
|---|---:|---:|---:|---:|
| 하단고기집 | 1 | 0.566267 | **0.504472** | 0.421401 |
| 하단삼겹살 | 1 | 0.574134 | **0.504472** | 0.424370 |
| 하단맛집 | 13 | 0.368931 | **0.504472** | 0.365972 |

### N2 교차 검증

동일 MID가 동시에 존재하는 업체들을 전수 비교한 결과:

- `하단고기집 ↔ 하단삼겹살`: 공통 MID **28개 / 28개 N2 완전 동일**
- `하단고기집 ↔ 하단맛집`: 공통 MID **18개 / 18개 N2 완전 동일**
- `하단삼겹살 ↔ 하단맛집`: 공통 MID **12개 / 12개 N2 완전 동일**

현재 표본에서는 소수점 6자리까지 차이가 0이었다.

### 현재 가장 강한 가설

- **N1 = Query × Place 성격의 값**
  - 키워드가 바뀌면 같은 MID라도 크게 변함.
  - 유사도 계열이라는 ADLOG 설명과 방향이 맞음.
- **N2 = Place × Time 성격의 값**
  - 같은 시점의 동일 MID에서는 서로 다른 키워드에서도 동일하게 관측됨.
  - 고정 상수가 아니라 날짜에 따라 변하는 기록이 있으므로 플레이스 자체 상태/활성 신호 계열로 추정.
- **N3 = 랭킹/최종 정렬 계열 값**
  - 키워드별 순위와 강하게 정렬되는 모습.
  - N1/N2를 포함한 결합값일 가능성이 높지만 정확한 공식은 아직 미확정.

개념적으로 현재 가장 유력한 구조:

```text
검색 키워드 ──> N1 (Query × Place)
                    \
                     -> N3 (랭킹 계열) -> 순위
                    /
플레이스 상태 ─> N2 (Place × Time)
```

## 4. 추가로 발견한 N1 특징

`하단맛집` 50개 결과에서는 N1이 대부분 `0.368931` 또는 `0.368977` 부근으로 매우 좁게 모였다.

반대로 `하단고기집`, `하단삼겹살`에서는 업체별 N1 차이가 더 크게 나타났다.

따라서 N1을 단순한 업체명-키워드 문자열 유사도로 보면 설명이 부족할 수 있다. 현재 후보:

- 검색 키워드/검색군별 baseline
- 카테고리/업종 적합도
- 업체 상세 키워드 및 업체정보 매칭
- 기타 네이버 검색 로직 기반 보정

정확한 계산법은 미확정.

## 5. N3 공식 상태

과거 일부 시계열 표본에서는 아래 형태가 매우 잘 맞는 경우가 있었다.

```text
N3 ≈ (10 + 20*N1 + 2*N2) / 53
```

하지만 현재 교차 키워드 표본, 특히 `하단맛집`에서는 단일 고정식으로 전체를 설명하기 어렵다.

따라서 현재 PLANKING에서는 이 식을 **확정 공식으로 취급하지 않는다.** 키워드 그룹별 보정/추가 변수 가능성을 열어둔다.

## 6. PLANKING 구현 원칙

연구가 더 진행되기 전까지:

- 순위: 실제 수집값으로 표시
- 방문자(영수증) 리뷰 / 블로그 리뷰 / 저장: Naver GraphQL 실측값으로 수집 가능
- N1/N2/N3: `PLANKING 실험 지수` 또는 출처/신뢰도를 함께 표시
- N1/N2/N3를 네이버 공식 점수라고 표기하지 않음
- 미관측 키워드에 대해 생성되는 값은 `estimated`로 구분

현재 DB/엔진 설계 방향은 다음처럼 분리하는 것이 타당하다.

```text
rank_history
  keyword × MID × date

place_metrics_history
  MID × date
  - visitor_review_count
  - blog_review_count
  - save_count

place_index_history
  keyword × MID × date
  - n1
  - n2
  - n3
  - source/confidence
```
